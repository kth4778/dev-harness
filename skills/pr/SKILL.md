# PR (Phase 6)

**기능 하나 = PR 하나.**

## 경계는 줄 수가 아니라 기능이다

| | 예 |
|---|---|
| **다른 PR로** | 로그인 · 인증 · 결제 · 회원가입 — 각각 독립된 기능이다 |
| **같은 PR로** | 로그인 안의 컨트롤러·서비스·엔티티·마이그레이션·테스트 |

**한 기능 안에서는 줄이 많아도 쪼개지 않는다.** 쪼개면 봇 리뷰 라운드가 PR 수만큼
곱해지고, 코드와 그 코드를 검증하는 테스트가 갈라져 앞 PR이 검증 없이 머지된다.

**여러 기능을 한 PR에 묶지도 않는다.** 리뷰어가 어디부터 봐야 할지 모르고,
한 기능에 문제가 있으면 나머지도 같이 막힌다.

기능의 경계는 이미 Phase 1(구체화)의 토폴로지 게이트에서 사용자와 함께
확정했다. 여기서 다시 정하지 않는다. PR이 그 경계와 맞는지만 확인한다.

줄 수가 많아 불안하면 그건 **기능이 하나가 맞는지** 다시 볼 신호이지,
쪼갤 신호가 아니다. 실제로 둘 이상이면 다음 세션으로 미룬다.

## 1. 커밋 정리 — 여기서는 확인만 한다

`inspect`에서 커밋 단위가 PASS했으면 건드리지 않는다.

**정리가 남아 있으면 Phase 5로 돌아간다.** 여기서 고쳐 쓰면 이미 검사를
통과한 이력이 검사 없이 바뀐다. 접는 자리는 Phase 5 한 곳이다(규칙 2).

## 1.5 PR을 바로 열지 않는다 — 로컬 `/code-review` 루프로 봇이 볼 것을 미리 잡는다

**봇은 확인 도장을 받는 자리지 수리공이 아니다.** 봇 지적 한 라운드는 새 PR 하나 =
리뷰 2회 = 수십 분이고, 라운드마다 봇은 바뀐 코드 주변을 다시 파서 새 지적을 낸다.
같은 것을 로컬에서 먼저 돌리면 한 라운드가 몇 분이다.

두 세션이 이 절차로 판수를 줄였다 — POK-116(2026-08-16) 로컬 4라운드 → PR **1판** ·
POK-93(2026-08-17) 로컬 3라운드(사소 44 → 28 고침) → PR **2판**. 그 전 POK-84는
로컬 루프 없이 **7판**이었다. 둘 다 사용자가 직접 설계해 지시했다 — 그래서 여기 박는다.

### 반복 루프

```
1. **`/code-review high` 스킬을 실제로 호출한다** — 직접 diff를 읽는 것으로 대신하지 않는다(아래 1-1)
2. 지적 하나하나를 검토한다 — **심각도를 매기려면 재현한다**(아래 2-1)
   ┌ 「맞다, 고친다」: 정상 운영에서 유실·잘못된 카운터 / 이 PR이 새로 만든 회귀 /
   │                 국소 수정 / 보안·유출
   └ 「기각」: 장애 둘 겹침 / 우리가 안 쓰는 옵션 / 구조를 또 바꿔야 하는 것 / 사실과 다른 지적
              → 왜 틀렸는지 근거와 함께 기록한다
3. 고칠 지적을 사용자에게 쉽게 설명하고 고친다 — 테스트 먼저 빨간불 → 초록 → 전체 테스트
4. 다시 /code-review → 2·3 반복
5. 종료: 한 라운드에서 **① 「맞다, 고친다」에 드는 치명·중대가 0이고 ② 「재현 못 함」이 하나도
   안 남았을 때** 끝난다. 사소는 마지막 라운드에 모아 고친다 — **재현 못 한 것은 그냥 통과시키지
   않는다**(아래 2-2)
6. 회귀 신호(라운드당 지적 수가 안 줄거나, 지적 출처가 내 직전 수정)가 켜지면 다음 라운드를
   돌기 전에 사용자에게 셋 중 택일을 묻는다 — 계속 / 수용 기준 세우기 / 여기서 멈추고 기록
   (RULES.md 「수정이 회귀를 만들기 시작하면 멈춘다」의 묻는 형식과 같다)
```

### 1-1. 🔴 라운드마다 스킬을 실제로 호출한다 — 「같은 일을 했다」는 안 통한다

**직접 diff를 읽고 「스킬이 할 일을 했다」고 여기면 안 된다.** 2026-08-20에 로컬 리뷰
5라운드 중 **3·4라운드를 스킬 없이** 돌렸다. 결과가 비슷해 보였고 그래서 스스로도 몰랐다 —
사용자가 *"./code-review 스킬 써서 한 거 맞아?"*로 물어 드러났다.

**스킬은 내가 안 보는 것을 본다.** 그 세션에서 스킬로 돌린 1라운드는 정확성 결함 3건을
냈는데, 손으로 읽은 3·4라운드는 **내가 방금 고친 자리 주변만** 봤다. 같은 절차가 아니다.

**라운드 기록에 호출 사실을 남긴다.** `_workspace/1N_review_round{N}.md` 머리에 한 줄:

```markdown
`/code-review high` 호출 — 라운드 N
```

호출 안 한 라운드는 **라운드로 세지 않는다.** 「5라운드 돌렸다」가 실제로는 3라운드였다는
것이 그렇게 드러났다.

### 2-1. 🔴 심각도를 매기려면 재현한다 — 오케스트레이터 자신에게도 걸린다

**"필요하면 재현한다"로는 안 지켜졌다. 세 번째다.**

| 언제 | 무엇 |
|---|---|
| 2026-08-09 | 없는 결함을 코드 논증만으로 **중대**로 판정 → 고칠 필요 없는 코드를 고쳤고 검토가 한 바퀴 더 돌았다 |
| 2026-08-18 (POK-82) | 봇 지적 넷을 코드만 읽고 *"넷 다 타당, P1은 중대"*로 보고 → 사용자가 되물어 재현하니 **하나는 절반이 틀렸고**(봇이 주장한 기본형 매핑이 사실이 아니었다) 다른 하나는 심각도가 내려갔다(health가 이미 드러내고 있었다) |

**규칙 자체는 2026-08-09에 만들어 `RULES.md` 4절에 넣었다.** 그런데 그것이
**에이전트 정의로만 흘렀다** — 오케스트레이터가 감사자·plan-critic에게 그 규칙을
주기만 하고 자기 판정에는 안 걸었다. 2026-08-18에 오케스트레이터가 직접 그 실수를
했고, 자기가 그날 감사자 정의에 옮겨 적은 규칙이었다.

**그래서 문안을 바꾼다.**

- **재현했으면** 심각도를 적는다
- **재현 못 했으면 심각도 자리에 「재현 못 함」을 적는다.** "타당해 보인다"·"중대로
  보인다"는 심각도가 아니다
- **이 규칙은 검토자·감사자뿐 아니라 오케스트레이터 자신에게 걸린다.** 봇 지적을
  사용자에게 옮길 때가 가장 새기 쉬운 자리다 — 봇이 이미 심각도 딱지를 붙여 왔기
  때문에 그것을 그대로 옮기면 판정한 것처럼 보인다

**봇이 둘이라고 검증이 두 번 된 것이 아니다.** POK-82에서 두 봇이 같은 P1을 독립적으로
지적했는데, 둘 다 **같은 미확인 가정** 위에 서 있었다("FIFO가 한 배치에 같은 그룹을
여러 개 준다"). 그 가정은 참이었지만 **아무도 확인하지 않은 채 "둘이 찾았으니 진짜"로
읽혔다.** 거짓이었다면 멀쩡한 코드를 고치고 라운드가 한 번 더 돌았다.

### 2-2. 🔴 「재현 못 함」은 게이트를 통과시키는 값이 아니다

**심각도를 지우면 그 지적이 이후 모든 게이트 밖으로 빠진다**(codex, PR #103 P1).
종료 조건(5단계)과 머지 체크리스트가 둘 다 **「심각한 것이 없나」**만 보므로,
심각도가 아예 없는 항목은 **아무 판단도 안 받고 조용히 통과한다.**

실제로 그렇게 지나갔다 — 2026-08-20에 봇 P1 하나를 「재현 못 함」으로 적고
게이트를 그냥 통과시켰다(고치기는 했지만 그것은 우연히 같은 메서드였기 때문이다).

**재현 못 한 지적은 셋 중 하나로 처분하고 그 사실을 적는다.**

| 처분 | 언제 |
|---|---|
| **그래도 고친다** | 고침이 국소적이거나, 맞다면 대가가 큰 것 |
| **사용자가 미루기로 했다** | 물었고 **답을 받았다.** 재현 조건과 무엇을 시도했는지 함께 기록 |
| **기각한다** | 봇의 전제가 사실과 다르다는 것을 **재현으로** 보였다 |

**어디에도 안 걸린 「재현 못 함」이 남아 있으면 루프를 끝내지 않는다.**
「못 쟀으니 모르겠다」는 처분이 아니다 — 모르는 채로 머지할지는 사용자가 정한다.

**수용 기준 표는 아래 4절 「봇 지적을 언제까지 고치나」와 같은 것이다.** 로컬에서
쓰는 잣대와 봇에게 쓰는 잣대가 다르면 로컬에서 넘긴 것이 봇에서 올라온다.

### 커밋은 남발하지 않는다

라운드마다 커밋하지 않는다. **작업 트리에 쌓아 두다가 종료 시점에 한 번** — 고친 것을
각각 해당 하위 기능 커밋에 `fixup`으로 접어 이력이 Phase 5가 판정한 커밋 수를 그대로
유지하게 한다(규칙 2 「왕복한 이력은 접는다」). **새 커밋을 얹지 않는다.** 배치 기준은
"그 파일을 처음 만든 태스크 커밋"이고, 컴파일이 안 되는 자리면 그 코드가 생긴 커밋으로.

끝난 뒤: **전체 테스트 5회 재확인 → `.harness/stamp` 갱신 → 그때 PR을 열지 사용자에게
다시 묻는다.** 접힌 커밋은 그 조합으로 돌아본 적이 없다 — 5회는 여기서도 생략하지 않는다.

### 기각한 것도 라운드별로 남긴다

`_workspace/1N_review_round{N}.md` — 지적마다 판정(고친다/기각)과 근거. **기각 근거는
봇 리뷰 때 같은 지적이 오면 그대로 답이 된다.** POK-93에서 봇의 P1 하나(갱신 거부 시
access revoke)가 로컬 라운드에서 이미 "설계 결정과 충돌"로 기각한 자리와 같았다.

## 2. PR 생성

통합 브랜치 이름을 박아두지 않는다. 저장소마다 다르다(`develop`인 곳도 `main`인 곳도 있다).

```bash
# Phase 5 가 검사한 값을 그대로 쓴다. origin/HEAD 는 기본값일 뿐이고,
# 프로젝트 CLAUDE.md 가 develop·release 를 통합 브랜치로 정했으면 다르다.
# <b>문서와 실물을 둘 다 구해 대조한다.</b> 문서만 믿으면 정책이 바뀐 뒤 낡은 값을
# 그대로 쓰고 fallback 에 영영 안 닿는다 — 아래 문단의 실패가 정확히 그것이다.
DOC=           # ← 프로젝트 CLAUDE.md 가 정한 통합 브랜치(적혀 있으면 여기 적는다)
LIVE=$(git symbolic-ref -q --short refs/remotes/origin/HEAD | sed 's|^origin/||')
BASE="${DOC:-$LIVE}"
if [ -n "$DOC" ] && [ "$DOC" != "$LIVE" ]; then
  echo "문서($DOC) 와 실물($LIVE) 이 다르다 — 어느 쪽이 맞는지 사용자에게 먼저 묻는다"
  exit 1
fi

# push 대상을 **여기서 한 번 정하고** 생성·정리가 같은 것을 쓴다.
# 생성은 origin 에 박고 정리는 pushDefault 를 따르면 서로 다른 저장소를 가리켜,
# 정작 PR 의 head 브랜치가 안 지워진다.
BR=$(git rev-parse --abbrev-ref HEAD)
REMOTE=$(git config "branch.$BR.pushRemote" || git config remote.pushDefault \
  || git config "branch.$BR.remote" || echo origin)

git push -u "$REMOTE" "$BR"
gh pr create --base "$BASE" --title "{타입}: {한 줄}" --body-file _workspace/pr-body.md
```

본문에 담을 것:

```markdown
## 무엇을
{한 문단}

## 왜
{이 결정을 한 이유. 대안을 버린 이유}

## 검증
- 테스트: {N}개 통과
- 서버 기동: 확인
- 주요 엔드포인트 호출: {결과 요약}

## 주의
{리뷰어가 알아야 할 함정·미완성 부분·의도적 단순화}
{알려진 결함·플레이키 — 숫자와 함께}
```

**`Co-Authored-By`를 넣지 않는다** (규칙 8).

### 본문에서 지킬 것 둘

**1) 커밋되지 않는 파일을 근거로 인용하지 않는다.**
`.claude/` · `_workspace/` · `_archive/` · `CLAUDE.md`(전 층)는 규칙 9로 커밋되지
않으므로 **리뷰어가 열 수 없다.** "자세한 것은 `모듈/CLAUDE.md`에 있습니다"·
"증거는 `_workspace/09_inspection_final.md`"는 리뷰어에게 빈 문장이다.
근거가 필요하면 **본문에 옮겨 적는다.**

올리기 전에 확인한다:

```bash
grep -nE '\.claude/|_workspace/|_archive/|CLAUDE\.md' _workspace/pr-body.md
```

**2) 알려진 결함·플레이키를 주의 절에 적는다.**
`inspect` 11번에서 "운영 전 과제"로 넘긴 것과, 이 PR과 인과가 없는 기존 플레이키가
대상이다. **특히 CI를 확률적으로 깨는 것은 반드시 적는다** — 안 적으면 리뷰어는
빨간불을 이 PR 탓으로 읽고, 그 오해를 푸는 데 라운드 하나가 나간다.

**숫자를 함께 적는다.** "가끔 실패합니다"가 아니라 "약 16분의 1로 헛통과하고,
원인은 …, 고치는 법은 …"이어야 읽힌다.

## 3. 봇이 무언가를 남겼는지 먼저 확인한다

**워크플로가 초록불인 것은 리뷰를 받았다는 증거가 아니다.**

2026-08-06에 claude 리뷰가 **다섯 겹으로 죽어 있었다.** 매번 잡은 `success`로
끝났고, `is_error=false`였고, 아무것도 안 올라왔다. 그 상태로 PR을 머지했으면
**"봇 둘에게 리뷰받았다"는 기록만 남고 실제 검토는 절반이었다.**

겹마다 증상이 달라 더 안 보였다 — 5턴 → 30턴 → 4턴 → 15턴으로 오갔고,
**제대로 고칠수록 조용해지기까지 했다**(우회 경로가 사라져서).

```bash
gh pr view <N> --json reviews  --jq '[.reviews[].author.login]  | unique'
gh api "repos/<owner>/<repo>/issues/<N>/comments" --jq '[.[].user.login] | unique'
gh api "repos/<owner>/<repo>/pulls/<N>/comments"  --jq '[.[].user.login] | unique'
```

**봇 하나가 세 곳 어디에도 없으면 리뷰를 안 받은 것이다.** 붙은 봇마다 확인한다.

| 보이는 것 | 뜻 |
|---|---|
| `## Code review / No issues found` | **정상이다.** 지적이 없어서 그런 것 |
| 아무것도 없음 | **리뷰가 안 돌았다.** 잡이 초록이어도 그렇다 |
| 인라인만 있고 요약이 없음 | 봇마다 다르다. 그 봇의 평소 모양과 비교한다 |

> **"코멘트 0"이 곧 고장은 아니다.** 지적할 것이 없으면 조용한 봇도 있다.
> 그래서 **평소에 무엇을 남기는 봇인지**를 알고 있어야 한다 — 과거 PR을 보면 된다.

### 🔴 PR을 올린 브랜치에는 push하지 않는다 — 봇마다 트리거가 다르다

> **예외 하나 — 심각한 지적이 하나도 없을 때(2026-08-17 사용자 결정).** 도착한 지적을
> 먼저 전부 타당성 검토하고 타당한 것만 모은다. 그중 **심각(치명·중대)이 하나라도 있으면**
> 타당한 것을 **모두** 고쳐 새 브랜치·새 PR로 다시 리뷰를 받는다(아래). **하나도 없으면**
> 타당한 것을 모두 고쳐 **같은 PR에 넣고**(fixup으로 접어 커밋 수 유지, `--force-with-lease`)
> 그대로 머지한다 — 새 PR을 열면 봇이 또 다른 자리를 파서 라운드만 는다. 봇이 그 push를
> 안 본다는 것은 감수하는 것이고, `merge-cleanup.py`가 「리뷰된 커밋 ≠ head」로 멈추면
> `gh pr merge --merge`로 직접 머지하고 정리(base 이동·pull·브랜치 삭제)를 손으로 한다.
> 상세는 `references/bot-review.md` 「흐름」.

| 봇 | 언제 도나 |
|---|---|
| **codex** | PR 생성 · draft→ready · `@codex review` 코멘트. **push로는 안 돈다** |
| **claudecode** | PR 생성 · draft→ready · reopen. **이 저장소는 push로 안 돈다** — 워크플로 트리거에 `synchronize`가 없다 |

**같은 브랜치에 push하면 둘 다 새로 안 돈다.** codex는 push를 트리거로 안 쓰고,
claudecode 워크플로는 `synchronize`를 트리거에서 빼 뒀다
([`.github/workflows/claude-code-review.yml`](../../.github/workflows/claude-code-review.yml)).
**두 리뷰가 옛 커밋에 그대로 머물고, 고친 코드는 아무도 안 본다.**

실측(2026-08-09, PR #42): push 뒤 codex는 앞 커밋에 머물렀고, claudecode는
**5턴·$0.15로 돌고 아무것도 안 남겼다**(첫 실행은 29턴·$12.25).

**고칠 것이 있으면 그 브랜치 위에 새 브랜치를 쌓고, 새 PR의 base는 통합 브랜치로
잡은 뒤 앞 PR을 닫는다. 스택 PR(base=기능 브랜치)을 만들지 마라 — claude 리뷰가
아예 안 돈다.**

> **통합 브랜치 이름을 여기 박지 않는다.** 2절과 같은 방법으로 그때 구한다 —
> 프로젝트 `CLAUDE.md`가 정한 값, 없으면
> `git symbolic-ref -q --short refs/remotes/origin/HEAD`.
> **문서는 정책이 바뀌는 순간 낡는다** — 2026-08-18에 한 저장소가
> `기능 → main`에서 `기능 → develop → main`으로 옮겼는데 2층 `CLAUDE.md`가
> 옛 값을 말하고 있었고, 그 값을 믿은 PR이 `main` 보호 게이트에 걸렸다.
> **같은 스킬 안에서 2절은 동적으로 구하고 여기만 `main`이 박혀 있었다.**

→ `references/bot-review.md`

> **PR 하나 = 리뷰 정확히 2회**가 그렇게 지켜진다. **워크플로를 고칠 필요가 없다** —
> 트리거를 막는 것이 아니라 **트리거될 사건 자체를 안 만드는** 것이라 더 강하다.

> **호출 코멘트를 달지 마라.** PR 을 열면 두 봇 다 자동으로 돈다 — 달면 claude 가
> 코멘트 트리거로 한 번 더 돌아 리뷰가 겹친다. 호출 토큰은 **자동 리뷰가 안 왔을
> 때 재촉용**으로만 쓴다(규칙 10 예외).

리뷰가 안 왔으면 **머지하지 말고 워크플로부터 고친다.**
`show_full_output` 류의 진단이 필요할 수 있고, **워크플로를 고치는 PR은
자기 자신을 검증하지 못한다**(액션이 기본 브랜치와 내용이 다르면 실행을 거부한다).
머지한 뒤 **새 PR을 열어** 확인한다 — 이 워크플로는 `synchronize`를 안 받으므로
push로는 안 돈다. draft를 ready로 바꾸거나 닫힌 PR을 reopen해도 트리거된다.

→ [`references/bot-review.md`](references/bot-review.md) — 봇 리뷰 대응 규칙
(**브랜치 동결과 스택 PR**·심각도 판정·수용 판단·답글 금지·머지 뒤 지적)

## 4. GitHub의 "Commit suggestion" 버튼을 쓰지 않는다

**봇이 공동 저자로 기록된다** (규칙 8 위반). 제안이 맞으면 로컬에서 직접 고친다.

### 봇 지적을 언제까지 고치나 — 기준을 먼저 세운다

**"심각하면 고친다"만으로는 끝이 없다.** PokeClip POK-84(2026-08-15)에서 PR이
7판(#52→#58)까지 갔다 — 봇 지적 24건 중 P1이 7→3→1→2→3→3으로 **수렴하지 않았고**,
절반은 직전 라운드 수정이 만든 것이었다. 사용자가 *"절대 안 끝날 것 같은데
언제까지 수용해야 하나"*를 물은 뒤에야 기준을 세웠고, 그 기준으로 다음 판에서
끝났다. **처음부터 있었으면 두 판은 줄었다.**

| 고친다 | 미룬다 — 3층 `CLAUDE.md`와 PR 「주의」절에 재현 조건과 함께 기록 |
|---|---|
| **정상 운영에서** 데이터 유실·잘못된 카운터가 나는 것 | 장애가 **둘 이상 겹쳐야** 나는 것 (예: 영구 정지 직후 몇 마이크로초에 SIGTERM) |
| 이 PR이 **새로 만든** 회귀 | 우리가 **안 쓰는** 옵션·설정에서만 나는 것 |
| 고침이 국소적 — 한 파일, 수십 줄 | 고치려면 **구조를 또 바꿔야** 하는 것 — 다음 라운드 P1 제조기다 |
| 보안·유출 규칙 위반 (레벨 무관) | |

**P1 딱지는 기준이 아니다.** 봇의 심각도는 "그 시나리오에서의 결과"이지 "그
시나리오가 얼마나 현실적인가"가 아니다. 위 표의 왼쪽 열에 드는지를 본다.

**PR 판수가 3을 넘으면, 다음 라운드를 돌기 전에 이 표를 사용자에게 보여 주고
어느 열로 가를지 먼저 묻는다.** 그 자리에서 미룬 것은 3층 `CLAUDE.md`에 적고
다음 카드(같은 경로를 다시 만지는 카드)에 몰아 처리한다.

## 5. 머지

- CI 통과
- **봇 2개가 실제로 남긴 리뷰에 심각한 지적이 없음** (3번으로 확인한 것) — "심각"의
  판정은 위 표다. 오른쪽 열만 남으면 기록하고 머지한다
- 사용자 승인

**라운드가 여럿이면 마지막 PR 하나만 머지한다.** 브랜치가 앞의 것 위에 쌓여 있어
그 안에 전부 들어 있다. 앞 PR들은 이미 닫혀 있어야 한다.

### 🔴 접힌 이력인지 먼저 확인한다 (접기 자체는 Phase 5에서 끝난다)

**남길 단위는 하위 기능 하나당 커밋 하나다**(규칙 2). 기능과 그것을 검증하는
테스트가 **같은 커밋**에 들어간다 — 갈라면 `inspect`의 TDD 검사가 구현만 있는
커밋을 TDD 안 한 증거로 본다. 작업 중에는 TDD 사이클마다 커밋하고,
**올리기 전에 그 모양으로 접는다.**

**접는 자리는 Phase 5다.** `inspect` 2번이 커밋 수와 하위 기능 수를 비교해
FAIL을 내고, 그 자리에서 접는다 — 여기(Phase 6)에 오면 이미 접혀 있어야 한다.
PR을 올린 뒤에는 못 접으므로(아래 참고) Phase 5가 마지막 기회다.

```bash
# 위 2절과 같은 방법으로 구한다 — 문서와 실물을 대조하고 다르면 멈춘다.
DOC=           # ← 프로젝트 CLAUDE.md 가 정한 통합 브랜치(블록마다 다시 정한다)
LIVE=$(git symbolic-ref -q --short refs/remotes/origin/HEAD | sed 's|^origin/||')
BASE="${DOC:-$LIVE}"
[ -z "$DOC" ] || [ "$DOC" = "$LIVE" ] || { echo "문서와 실물이 다르다 — 먼저 확인한다"; exit 1; }
"${CLAUDE_PLUGIN_ROOT}/skills/inspect/scripts/check-branch-commits.py" "$BASE" --phase6 <PR번호>
```

**`--phase6 <PR번호>` 를 넘긴다.** 안 넘기면 지금 열린 이 PR 이 「이 브랜치로
이미 PR 이 열렸다」로 잡힌다. 반대로 Phase 5 에서는 넘기지 않는다 — 그때
열린 PR 이 있다면 그것은 **얼린 PR 에 커밋을 얹으려는 것**이라 막아야 한다.

**여기서도 스크립트를 부른다.** `git log "$BASE"..HEAD` 를 코드 블록에 두면
`BASE` 가 없어 `HEAD..HEAD` 로 읽히고 **커밋을 하나도 안 보여준다.**

**여기서 `rebase`를 돌리지 마라.** 이 자리는 PR을 올리고 봇 리뷰를 받은 뒤다 —
고쳐 쓰면 리뷰가 붙은 SHA가 사라진다. force push해도 워크플로에 `synchronize`가
없어 **리뷰는 옛 커밋에 남고**, push를 안 하면 원격 PR이 접히지 않은 채 머지된다.

**접혀 있지 않으면 Phase 5로 돌아간다.** 아직 push 전이면 거기서 접고,
이미 올렸으면 새 브랜치를 쌓아 접은 이력으로 새 PR을 연다(브랜치 동결).

**접을 것과 남길 것.**

| | 무엇 |
|---|---|
| **접는다** | 서로 상쇄하는 커밋(진단 켜기/끄기) · 같은 자리를 여러 번 고친 것 · 헛통과를 막는 test 커밋 |
| **남긴다** | 하위 기능 경계. 커밋 하나에 구현과 테스트가 함께 |

`rebase -i`에서 `squash`는 메시지를 합치고 `fixup`은 앞 커밋 메시지를 그대로
쓴다. **왕복 커밋은 `fixup`이다** — 그 메시지는 이력에 남을 가치가 없다.

접은 뒤 **테스트를 다시 돌린다.** 접힌 커밋은 한 번도 그 조합으로 돌아본 적이
없다. `inspect` 2번을 접기 **뒤에** 하는 이유가 이것이다.

> **이미 push한 뒤에는 접지 않는다.** force push는 봇 리뷰가 가리키는 커밋을
> 없애 리뷰가 통째로 떠 버린다. 접는 자리는 **첫 push 전** 한 번이다.
> 봇 지적을 받아 고칠 때는 새 브랜치를 쌓고(브랜치 동결), 그 브랜치에서
> 다시 접어 올린다.

**진행 기록이 태스크를 커밋 해시로 가리키면 접을 때 그 해시가 죽는다.**
`_workspace`의 진행 기록은 **커밋 제목**으로 가리킨다 — 아래 스쿼시 절이
같은 이유로 요구하는 것과 같다. 해시가 이미 적혀 있으면 접은 뒤 갱신한다.

### 🔴 머지와 정리는 스크립트로 한다

```bash
"${CLAUDE_PLUGIN_ROOT}/skills/pr/scripts/merge-cleanup.py" <PR번호>
```

**`${CLAUDE_PLUGIN_ROOT}` 를 붙인다.** 설치본으로 쓰면 작업 폴더는 대상
프로젝트이지 이 플러그인이 아니다 — 상대 경로로 부르면 없는 파일이 된다.
훅이 `run-hook.cmd` 를 그렇게 부르는 것과 같은 이유다.

**base 는 안 넘긴다.** 스크립트가 PR 에서 직접 읽는다.

**손으로 치지 않는다.** 이 절차를 문서 안 코드 블록으로 두었다가 같은 실수를
네 번 냈다 — 블록마다 새 셸이라 앞에서 정한 변수가 없었고, 문서라서 한 번도
안 돌려봤다. 스크립트는 `hooks/tests/cleanup.sh`가 **43갈래를 실제로 잰다.**

스크립트가 하는 일:

| | |
|---|---|
| 머지 | `--merge`(스쿼시 아님). **`--delete-branch`는 넘기지 않는다** — 삭제는 아래의 검증된 절차가 한다. 큐에 들어가면 끝나기를 기다린다 |
| 시한 | 요청마다 30초, 큐 대기는 20분. `gh`·`git` 둘 다 타임아웃 옵션이 없고 macOS에는 `timeout(1)`이 없어 직접 잰다 |
| 대조 | **PR 의 head 가 지금 브랜치와 같은지 먼저 본다.** 번호를 잘못 넣으면 상관없는 브랜치를 원격까지 지운다 |
| 고정 | `--match-head-commit` 으로 **리뷰가 붙은 커밋**에 묶는다. 리뷰 뒤 누가 push 했으면 거부한다 — 이 워크플로에는 `synchronize` 가 없어 그 커밋은 리뷰를 못 받는다 |
| 봇 확인 | 봇 둘이 **각각** 현재 head 를 봤는지 본다. 로그인을 **정확히** 대조한다 — `contains("claude")` 로 보면 `claude-review-helper` 같은 아무 계정이 통과한다 |
| SHA 없는 증거 | codex 가 👍 만, claude 가 코멘트만 남기는 경우가 있다(PR #33). 그것이 **현재 head** 를 본 것인지 기계가 알 수 없으므로 **자동으로 통과시키지 않고 멈춘다.** 눈으로 확인한 뒤 `CLEANUP_ALLOW_SHALESS=1` 로 다시 부른다. 반응은 `+1` 만 본다 — `eyes` 는 검토 시작 신호다 |
| 확인 | 명령이 성공해도 **상태를 직접 본다.** 큐에 넣기만 했거나 auto-merge 를 켜 둔 것일 수 있다 |
| 정리 | PR 의 base 로 옮긴 **뒤** 원격·로컬 브랜치를 지운다. head 를 올린 원격은 머지 **전에** 잡아둔다 |
| 전략 | 저장소가 merge commit 을 끄면 `--squash`·`--rebase` 로 떨어진다. `--merge` 만 두 번 시도하면 Phase 6 이 통째로 막힌다 |
| 삭제 | 원격**과 로컬**이 둘 다 리뷰된 커밋을 가리킬 때만 지운다. 큐를 기다리는 20분 사이에 원격에 push 가 오거나 다른 터미널이 로컬에 커밋을 얹으면 그것은 이 PR 에 없던 것이다 |
| 호스트 | push URL 의 **호스트까지** 대조한다. `owner/repo` 만 맞추면 github.com 과 사내 미러가 같아 보여 다른 서버의 동명 브랜치를 지운다 |
| 멈추는 곳 | head 불일치 · 조회 실패 · 큐에 못 넣음 · 머지가 안 끝남 · 브랜치 이동 실패 · 원격이 다른 커밋을 가리킴 · base 원격 없음. **그때는 아무것도 안 지운다** |

원격 브랜치가 **이미 없으면 성공으로 친다** — 머지 후 head를 자동 삭제하는
설정이 흔하다. 다만 `ls-remote`가 인증·전송 문제로 실패한 것과는 구분한다
(`--exit-code`의 2만 「없음」이다).

**스쿼시는 커밋 전부를 한 줄로 접는다.** 그러면 두 가지가 같이 사라진다.

1. **`inspect` 2번(커밋 단위)이 판정한 대상 자체**가 없어진다. "각 커밋 시점에
   테스트가 통과했다"를 나중에 아무도 확인할 수 없다
2. **`_workspace`·`_archive`가 적어 둔 커밋 해시가 죽는다.** 회고와 진행 기록은
   태스크를 해시로 가리키는데, 접히면 그 해시가 `main`에 없다

2026-08-09에 실제로 그렇게 됐다 — 32커밋이 1커밋이 됐고 진행 기록의 해시가
전부 못 여는 상태가 됐다. **브랜치를 지우는 순간 되찾을 방법도 사라진다.**

**스쿼시를 써야 한다면**(팀 규약이 그렇다면) 둘 중 하나를 한다.

- 아카이브가 해시 대신 **커밋 제목**으로 태스크를 가리키게 한다
- 접힌 이력을 태그로 남긴다 — 다만 **그 태그를 지우면 같은 문제**다

**문서 저장소(위키)는 스쿼시가 맞다.** 거기는 커밋 단위가 판정 대상이 아니다.

**머지 뒤에 손으로 더 할 것이 없다.** `merge-cleanup.py` 가 통합 브랜치로 옮기고,
검증한 원격에서 갱신하고, 원격·로컬 브랜치와 그 설정까지 지운다.

예전에는 여기에 수동 정리 블록이 있었는데 **걷어냈다**(2026-08-13, codex).
그 블록은 원격을 새로 구했는데, 그 시점에는 이미 통합 브랜치에 서 있어서
**head 가 아니라 base 의 설정**이 잡힌다. fork 처럼 둘이 다른 구성에서는
스크립트가 검증한 upstream 대신 fork 의 base 를 당겨 로컬을 오염시킨다.

정리가 중간에 멈췄으면 스크립트가 그 이유를 찍고 종료한다. 그때만 손으로 본다.

## 7. 티켓을 닫을 때는 부모와 형제를 같이 본다

**이번에 한 일이 티켓 하나로 끝나는 경우는 드물다.** 이슈 추적기를 쓰는
프로젝트면 카드가 에픽 → 스토리 → 하위 작업으로 겹쳐 있고, **닫은 카드만
바꾸면 보드는 여전히 틀린 그림을 보여 준다.**

2026-08-07에 하위 작업 하나를 완료로 바꾸고 "Jira 갱신 끝"이라고 보고했다.
사용자가 *"보드에 아직 진행 중인데"*라고 짚어서 셋이 더 나왔다.

| 어디 | 무엇이 틀려 있었나 |
|---|---|
| **형제 카드** | 시작도 안 한 것이 **「진행 중」**이었다 |
| **부모 에픽** | 자식 둘이 완료인데 **「할 일」**이었다 |
| **부모 스토리** | 완료 조건이 *"실측 로그를 **이 티켓** 코멘트에 남긴다"*인데 **코멘트가 0건**이었다 — 데이터는 자식 카드에만 있었다 |

**셋째가 가장 조용하다.** 부모의 완료 조건은 자식을 다 닫아도 저절로 안 채워진다.

**닫기 전에 넷을 본다.**

```
1. 이 카드의 완료 조건    전부 충족했나. 못 한 것은 못 했다고 적었나
2. 부모의 완료 조건       이 카드가 채워야 할 칸이 있나 — 특히 "이 티켓에 남긴다"류
3. 형제 카드의 상태       실제로 안 하고 있는 것이 "진행 중"으로 떠 있지 않나
4. 부모의 상태            자식이 움직였는데 부모가 안 움직였나
```

**인계 사항은 받는 카드에도 적는다.** 이번에 넘길 것을 **닫는 카드의 코멘트에만**
적어 뒀는데, 그 카드를 여는 사람은 앞 카드의 코멘트를 안 읽는다.
받는 쪽 카드에 같은 내용을 남긴다.

**남의 카드 상태는 바꾸지 않는다.** 내 담당 영역 밖이면 채팅으로 보고한다.
