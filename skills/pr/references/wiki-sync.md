## 6. 지식 위키 반영

코드 저장소 **밖에** 팀 지식 정본이 따로 있으면 여기서 맞춘다.

### 왜 별도 PR인가

규칙 6-2는 커밋되는 문서를 코드와 **같은 PR**에 태우라고 한다. 위키에는 그
규칙이 닿지 않는다 — **다른 저장소라 한 PR에 담을 수 없다.**

그래서 코드만 머지되고 정본은 옛 사실을 말하는 상태가 남는다. 실제로 그랬다 —
팀 계약의 엔드포인트 이름이 구현과 갈린 채로 있었고, 결정 문서의 "반영 완료"
체크가 사실이 아니었다. 둘 다 다음 사람이 그대로 읽고 짜면 깨지는 것이었다.

### 위키가 어디 있나

`<git루트>/.harness/wiki` 한 줄이 가리킨다. **없으면 이 단계를 건너뛴다** —
위키가 없는 프로젝트가 정상이다.

```bash
GIT_ROOT=$(git rev-parse --show-toplevel)
WIKI=$(head -n1 "$GIT_ROOT/.harness/wiki" 2>/dev/null | tr -d '\r')
[ -n "$WIKI" ] || { echo "위키 미설정 — 건너뛴다"; exit 0; }
cd "$GIT_ROOT/$WIKI" || exit 1
git remote -v    # 코드 저장소와 다른 곳을 가리켜야 한다
```

`.harness/root`와 같은 방식이다. 위키는 보통 형제 디렉터리에 클론돼 있으므로
`../PokeClip-LLM-WIKI`처럼 적는다. **조직 저장소일 수 있다** — 개인 저장소와
권한·리뷰 규칙이 다르므로 remote를 눈으로 확인하고 시작한다.

### 무엇을 훑나

**전체를 훑는다.** 이번 PR이 바꾼 것에서 출발하되 거기서 멈추지 않는다 —
위키는 컴파일도 테스트도 안 되므로 틀린 서술이 몇 달을 조용히 산다.

아래 신호를 **모든 파일에** 대고 본다. 이번 PR이 바꾼 사실은 그중 가장
걸리기 쉬운 자리일 뿐이다.

| 신호 | 예 |
|---|---|
| 팀원 간 계약이 바뀌었다 | 엔드포인트 이름 · 응답 형식 · 인증 헤더 |
| 구현이 결정 문서와 다르게 나갔다 | ADR은 A를 적었는데 B로 구현됐다 |
| 결정 문서의 후속 체크가 사실이 아니다 | "반영 완료"인데 대상 문서가 그대로다 |
| 상태가 바뀌었다 | 미구현 → 구현 완료 · 열린 미결이 닫혔다 |
| 다음 사람이 읽고 잘못 짤 곳 | 구현과 **반대 경로**를 적어 둔 절 |

**고칠 것이 없으면 "확인함"으로 끝낸다.** 억지로 만들지 않는다.

### 위키 저장소의 규약을 따른다

위키에는 그 저장소의 규약이 따로 있다. 코드 저장소의 관례를 가져가지 않는다.

시작 전에 읽을 것 — 위키 루트의 `CLAUDE.md`(또는 `README.md`) · 검사 스크립트 ·
인덱스 파일.

예로 PokeClip 위키는 **셋이 한 커밋**이다: 전문(`adr/`) + 인덱스(`decisions.md`
또는 `contracts.md`) + 현재 상태(`status.md`). 하나만 고치면 CI가 막는다.
커밋 전에 검사 스크립트를 돌린다.

```bash
PYTHONIOENCODING=utf-8 python scripts/check_docs.py   # 저장소마다 다르다. 규약 문서가 명령을 정한다
```

> 🔴 **`PYTHONIOENCODING=utf-8`을 빼지 마라.** Windows 콘솔은 cp949라 검사기가
> 한글을 출력하는 순간 **스크립트가 죽고 `exit=1`이 난다.** 그러면 「검사 실패」와
> 「인코딩 사고」가 구분되지 않는다 — 2026-08-09에 실제로 그렇게 한 바퀴 돌았다.
> 같은 함정이 테스트 결과 집계에서 이미 네 번 원인을 삼켰다(`inspect` 참고).
> **`exit=1`을 보면 먼저 인코딩부터 의심한다.**

### 내 영역만 고친다

전수로 훑는 것과 전수로 고치는 것은 다르다. **훑는 범위는 전체, 고치는 범위는
내 담당 영역이다.**

| 찾은 것 | 어디 것 | 무엇을 하나 |
|---|---|---|
| 오타 · 끊긴 링크 · 틀린 이름 · 죽은 체크 | **내 영역** | 고친다 |
| 같은 것 | **남의 영역** | 손대지 않는다. **채팅으로 보고** |
| 결정을 뒤집는 것 | 어디든 | 고치지 않는다. 새 결정 문서가 필요하고 그것은 소유자의 몫이다 |

**남의 영역은 오타라도 손대지 않는다.** Jira 카드와 같은 기준이다(`SKILL.md`
7절). 고쳐 주는 것이 친절해 보이지만, 그 문서의 소유자는 자기가 안 쓴 변경이
자기 영역에 들어온 것을 나중에 발견한다.

**내 영역이 어디인가는 위키 저장소의 규약이 정한다.** CODEOWNERS · 문서 머리말의
담당자 · 디렉터리 구분 중 그 저장소가 쓰는 것을 따른다. 판단이 안 서면 남의
것으로 보고 보고한다 — 안 고쳐서 생기는 손해가 잘못 고쳐서 생기는 손해보다 작다.

승인이 필요한 것은 PR 본문에 **"승인 필요"로 명시**하고 채팅으로도 보고한다.
조용히 고쳐 두면 승인 절차 자체가 사라진다.

### 올린다

브랜치 → 커밋 → push → PR. 코드 PR과 **같은 규칙이 그대로** 적용된다
(규칙 1 브랜치 · 2 단위 · 8 공동저자 금지 · 10 사람 계정 리뷰 금지).

본문에는 **수정마다 실제 근거**를 단다. 전수로 훑으므로 두 종류가 섞인다 —
근거를 안 가르면 리뷰어가 잘못된 이력을 읽는다(codex, PR #75).

| 수정의 성격 | 근거 |
|---|---|
| 이번 코드 PR 이 바꾼 사실 | **그 코드 PR 링크** |
| 전수 검사에서 찾은 기존 오류 | 「전수 검사에서 발견」이라 적고 **무엇이 왜 틀렸는지** 한 줄 |

기존 오류 수정에 코드 PR 링크만 걸면, 그 PR 이 그 오류까지 유발했다는
거짓 이력이 남는다. 근거 없는 수정은 올리지 않는다.
