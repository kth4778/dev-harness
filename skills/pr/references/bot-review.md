## 3. 봇 리뷰 대응

### 🔴 PR을 올린 브랜치에는 push하지 않는다

**PR 하나가 받는 리뷰는 정확히 2회다** — 생성 시 claudecode 1 + codex 1.
그 수를 지키는 방법은 워크플로를 고치는 것이 아니라 **push를 안 하는 것**이다.

**PR을 만든 순간 그 브랜치는 동결된다.** 고칠 것이 있으면 **새 브랜치를 그 위에 쌓고,
`main`을 base로 새 PR을 연 뒤 앞 PR을 닫는다.**

| 봇 | 언제 도나 |
|---|---|
| **codex** | **PR 생성·ready 전환·`@codex review` 코멘트뿐.** push로는 **안 돈다** |
| **claudecode** | PR 생성 · draft→ready · reopen. **push로는 안 돈다** — 워크플로 트리거에 `synchronize`가 없다 |

**둘 다 push를 트리거로 안 쓴다는 것이 이 규칙의 근거다.** 같은 브랜치에
push하면 **두 리뷰가 옛 커밋에 그대로 머물고, 고친 코드는 아무도 안 본다.**

실측(2026-08-09, PR #42): push 뒤 codex는 앞 커밋에 머물렀다. claudecode는
그때 트리거에 `synchronize`가 있어 돌긴 했으나 **5턴·$0.15로 아무것도 안
남겼다**(첫 실행은 29턴·$12.25). 그 뒤 워크플로에서 `synchronize`를 뺐으므로
지금은 아예 안 돈다.

> **호출 코멘트로 트리거하지 마라.** 새 PR을 여는 것이 유일한 정상 경로다 —
> PR 이 열리면 두 봇 다 자동으로 돌고, 호출을 달면 claude 가 코멘트 트리거로 한 번
> 더 돌아 리뷰가 겹친다. 호출 토큰은 자동 리뷰가 안 왔을 때 재촉용뿐이다(규칙 10 예외).

### 흐름

```
개발 완료 → (PR 전 로컬 /code-review 루프 — SKILL.md 1.5절) → PR ─── 리뷰 2회 ───┐
                                                                                 │
                       ① 지적을 전부 읽고 타당성 검토 — 타당한 것만 모은다        │
                              (틀린 지적은 근거와 함께 기각·기록)                 │
                                              │                                  │
              ┌───────────────────────────────┴───────────────────────────────┐
     타당한 것 중 심각(치명·중대) 없음                          심각이 하나라도 있음
              │                                                               │
   타당한 것을 모두 고쳐 같은 PR에                          타당한 것을 모두 고쳐
   (fixup 접기·force-with-lease) → 머지                    앞 브랜치 위에 새 브랜치
                                                      → main을 base로 새 PR → 또 리뷰 2회
                                                            (앞 PR은 닫는다)
                                                                     │
                                                              없을 때까지 반복
```

**지적이 도착하면 하나씩 고치지 않는다.** 전부 읽고 → 각각 판정하고
(맞나 / 틀렸나 / 확인 불가) → **타당한 것을 전부 고쳐** 한 번에 올린다.
쪼개면 PR 수만큼 리뷰 라운드가 곱해진다.

**심각이 없을 때 같은 PR에 push하는 것은 2026-08-17 사용자 결정이다**(POK-93 2판).
그 전 규칙은 "경미는 넘어가고 그대로 머지"였는데, 사용자가 "타당하면 고쳐야 하는 것이고,
새 PR을 열면 또 다른 자리를 판다"로 바꿨다. 봇이 그 push를 안 본다는 것은 감수한다 —
고친 것이 전부 사소·국소라는 것이 전제다.

### 🔴 PR의 base는 **언제나 통합 브랜치**다. 스택 PR을 만들지 마라

브랜치는 앞 브랜치 위에 계속 쌓되, **PR은 매번 `main`(통합 브랜치)을 base로 새로 열고
앞 PR은 닫는다.**

```
브랜치        feat/x ← fix/x-r1 ← fix/x-r2      (계속 쌓는다)
PR    1라운드  feat/x   → main      리뷰 2회 → 닫는다
      2라운드  fix/x-r1 → main      리뷰 2회 → 닫는다
      3라운드  fix/x-r2 → main      리뷰 2회 → 머지
```

**머지는 마지막 하나만** 한다. 그 안에 앞의 것이 다 들어 있다.

> **왜 스택이 아닌가 — claude 리뷰가 아예 안 돈다** (2026-08-09 실측).
>
> | PR | base | claude(Actions) | codex(앱) |
> |---|---|---|---|
> | #15 | `main` | ✅ 1회 | ✅ 1회 |
> | **#16** | **기능 브랜치** | 🔴 **0회** | ✅ 1회 |
> | #17 | `main` | ✅ 1회 | ✅ 1회 |
>
> **codex는 GitHub 앱이라 base와 무관하게 돌지만, claude는 GitHub Actions다.**
> base가 기본 브랜치가 아니면 워크플로 자체가 트리거되지 않는다 — 재오픈으로도 안 걸렸다.
> 워크플로 파일·YAML·트리거·권한은 전부 정상이었다.
>
> **스택을 쓰면 2라운드부터 검사 축이 절반으로 준다.** 실제로 그 PR에서
> claude만 짚은 지적이 3건 있었다.

**대가는 안다** — 마지막 PR 하나에 「기능」과 「수정」이 같은 diff로 섞인다.
그래도 **리뷰를 못 받는 것보다 낫다.** PR 본문에 라운드별로 무엇이 왜 바뀌었는지 적는다.

> 🔴 **브랜치 이름은 ASCII여야 한다.** `anthropics/claude-code-action`이
> **base 브랜치 이름을 검증하고 비ASCII를 거부한다** — `Invalid branch name`으로
> 잡이 27초 만에 실패한다(2026-08-09 실측). base일 때만 터지므로
> **head가 한글인 PR은 멀쩡히 돌아 안 보인다.**

**각 PR 본문에 무엇의 후속인지와 머지 순서를 적는다.** 안 적으면 리뷰어가
베이스 브랜치를 보고 역추적해야 한다.

### 머지된 뒤에 온 지적

PR이 닫힌 뒤에도 지적이 남아 있거나 새로 도착한다.

| 시점 | 처리 |
|---|---|
| PR이 열려 있다 | **심각한 것이 있으면 새 PR(base=main).** 없으면 머지 (위) |
| **머지된 뒤다** | **심각한 것만** 새 브랜치로 후속 PR. 나머지는 넘어간다 |

머지된 PR의 브랜치는 지워졌고, 되살려 push해도 닫힌 PR에는 붙지 않는다.

### 심각도 판정 — **새 PR을 열지 말지를 이것으로 정한다**

| | |
|---|---|
| **고친다** | 동작이 틀림 · 보안 구멍이나 시크릿 노출 · 데이터 유실·정합성 파손 · 테스트가 헛통과 · 문서가 다음 사람을 잘못 인도(계약·엔드포인트 이름 같은 것) |
| **넘어간다** | 취향·네이밍·스타일 · "이렇게도 가능" · 범위 밖 리팩터링 권유 · 이미 근거를 두고 그렇게 한 것 |

**판정 기준은 "그대로 두면 누가 무엇을 잘못하나"다.** 그 문장을 못 채우면
심각하지 않은 것이다.

**심각한 것이 하나라도 있으면 지적된 것을 전부 고친다.** 골라 고치면 남은
것이 다음 라운드에 그대로 다시 올라온다.

**심각한 것이 하나도 없으면 새 PR을 열지 않는다.** 타당한 사소 지적은 **고쳐서 같은 PR에
넣고**(fixup으로 접어 커밋 수 유지) 머지한다 — 경미한 지적 때문에 PR을 하나 더 만들면 리뷰가
2회 더 도는데 얻는 것이 없다. **기각한 것은 채팅으로 보고한다** — 무엇을 왜 넘겼는지.
조용히 버리지 않는다.

### 고칠 때 하네스를 다시 돌리지 않는다

**PR을 올린 그 세션이 그 자리에서 고친다.** Phase 1(구체화)로 되돌아가지 않는다.

설계와 계획은 이미 끝났고, 봇 지적은 그 결과물에 대한 것이다. 파이프라인을
재시작하면 산출물만 다시 쌓이고 실제로 바뀌는 것은 몇 줄이다.

**예외는 지적이 설계를 뒤집을 때다.** 그건 봇 지적이 아니라 새 기능이므로,
사용자에게 보고하고 다음 세션으로 넘긴다.

### 지적을 무조건 수용하지 않는다

봇은 이 코드베이스의 맥락을 모른다. 고치기 전에 확인한다.

- 이 코드베이스에서 기술적으로 맞는 말인가
- 기존 동작을 깨뜨리지 않나
- 지금 구현에 그렇게 한 이유가 있지 않나
- 쓰이지 않는 기능을 "제대로 구현하라"고 하는 건 아닌가 — 안 쓰면 지우는 게 맞다

틀렸다고 판단하면 **기술적 근거를 들어 반박**한다. 확인할 수 없으면 그렇다고
말하고 사람에게 묻는다.

### 앞의 지적을 수용하다 뒤를 깨뜨리지 않는다

"쓰이지 않으니 지워라"는 지적을 받아들여 지웠는데, 그게 뒤에서 쓰이는
경우가 있다. **지우기 전에 참조를 전부 찾는다.**

### 사람 계정으로 답글을 달지 않는다

`gh pr review`·`gh pr comment`는 훅이 막는다 (규칙 10).
고친 내용은 **채팅으로 보고**한다.

### 하지 않는 말

- "맞는 말씀입니다" · "좋은 지적입니다" · "감사합니다"
- 고쳤으면 무엇을 어떻게 고쳤는지만 말한다. 행동이 답이다
