# 구체화 (Phase 1)

추상적인 요청을 검증 가능한 설계로 바꾼다. 목적은 하나다 —
**AI가 마음대로 가정하고 개발하는 것을 막는 것.**

"로그인 기능"이라는 다섯 글자 안에는 결정되지 않은 게 최소 열 개 있다.
소셜 로그인 여부, 제공자, 수집할 정보, 토큰 방식과 수명, 비밀번호 정책,
실패 잠금, 기존 인증 스텁의 처리. 이걸 내가 정하면 그건 사용자의 제품이 아니다.

## 순서

### 1. 코드베이스를 먼저 조사한다

**사용자에게 묻기 전에 파일에서 찾는다.** 파일을 보면 아는 것을 질문으로
낭비하면, 사용자는 자기 코드를 다시 설명해야 한다.

조사할 것: 관련 기존 코드, 데이터 모델, 이미 깔린 의존성, 비슷한 기능의 선례.

조사 결과는 질문할 때 **근거로 인용**한다.
- 나쁜 예: "기존에 사용자 테이블이 있나요?"
- 좋은 예: "`users` 테이블에 `login_id`만 있고 비밀번호 컬럼이 없습니다.
  자체 계정 로그인을 넣으면 컬럼 추가가 필요한데, 이번 범위에 포함할까요?"

### 2. 토폴로지 게이트 — 딱 한 번

첫 질문 전에 **최상위 구성요소를 나열하고 확정받는다.**

```
이 요청을 3개 구성요소로 읽었습니다:
1. 소셜 로그인 — 외부 제공자로 인증
2. 자체 계정 — 아이디/비밀번호
3. 회원정보 관리 — 조회·수정·탈퇴

맞습니까? 추가·제거·병합·분리·보류할 것이 있습니까?
```

**왜 필요한가:** 이게 없으면 질문이 가장 많이 설명된 구성요소로 쏠린다.
로그인을 깊게 파는 동안 회원정보는 통째로 모호한 채 남고, 그 상태로 개발이
시작된다. 구성요소는 1~6개가 적정하다. 넘으면 묶는다.

보류(defer)로 정해진 구성요소는 점수 계산에서 빼되 **문서에는 남긴다** —
"이번에 안 한다"는 것도 결정이다.

### 3. 한 번에 한 질문

**절대 여러 질문을 묶지 않는다.** 묶으면 사용자가 앞의 것만 답하고,
뒤의 것은 내가 알아서 가정하게 된다.

네 차원을 각각 0.0~1.0으로 채점한다.

| 차원 | 판정 질문 |
|---|---|
| **목표** | 목표를 단서 없이 한 문장으로 말할 수 있나? 핵심 명사와 그 관계를 모호함 없이 댈 수 있나? |
| **제약** | 경계·한계·**비목표**가 분명한가? 무엇을 **안 하는지** 아는가? |
| **성공 기준** | 성공을 검증하는 **테스트를 지금 쓸 수 있나**? 수용 기준이 구체적인가? |
| **맥락** | (기존 코드 수정 시) 안전하게 고칠 만큼 시스템을 이해했나? |

매 질문마다 이 형식으로 시작한다.

```
[3라운드] 가장 약한 차원: 제약 (0.4)
비목표가 정해지지 않아 범위가 열려 있습니다. 그래서 이걸 묻습니다.

비밀번호 찾기·이메일 인증을 이번 범위에 넣습니까?
  A. 둘 다 이번에      B. 비밀번호 찾기만
  C. 둘 다 다음에      D. 기타

현재 점수 — 목표 0.8 / 제약 0.4 / 성공기준 0.6 / 맥락 0.9
```

**점수를 매번 공개한다.** 사용자가 "이제 그만 물어도 되겠다"를 스스로
판단할 수 있어야 한다.

선택지를 줄 수 있으면 준다. 열린 질문보다 답하기 쉽고, 내가 무엇을
고민하는지 사용자에게 보인다.

### 4. 임계값 게이트

**네 차원 모두 0.8 이상이 되기 전에는 Phase 2로 가지 않는다.**

사용자가 "그만하고 시작해"라고 하면 멈춘다. 다만 그때는 **미해결 항목을
가정으로 명시**하고 그 가정을 문서에 남긴다. 조용히 넘어가지 않는다.

```
알겠습니다. 다음 두 가지를 가정하고 진행합니다:
- 소셜 로그인은 이번 범위 밖 (2차)
- 토큰 수명은 access 30분 / refresh 14일

틀리면 지금 말씀해 주세요. 나중에 바꾸면 스키마부터 다시 갑니다.
```

### 5. 설계 제시 — 조각으로 나눠서

한 번에 다 쏟지 않는다. 복잡도에 맞춰 나누고 **조각마다 확인**받는다.

다룰 것: 구조, 구성요소, 데이터 흐름, 오류 처리, 테스트 방법.
