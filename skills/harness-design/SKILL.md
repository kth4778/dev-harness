# 하네스 설계 (Phase 3)

확정된 계획을 보고 **이 기능 전용 에이전트 팀**을 만든다.
역할은 계획이 결정한다 — 미리 정해둔 명단을 재사용하지 않는다.

**핵심 구분:** 스킬은 "어떻게 하는가", 에이전트는 "누가 하는가".

## 0. 현황 감사

```bash
ls .claude/agents/ 2>/dev/null
ls _workspace/ 2>/dev/null
```

| 상태 | 조치 |
|---|---|
| 둘 다 비었음 | 정상. 1번으로 진행 |
| `.claude/agents/`에 파일이 있음 | 지난 세션이 마감되지 않았다. `wrap` 스킬로 마감하고 다시 온다 |

## 1. 계획에서 역할을 뽑는다

계획의 태스크 목록을 읽고 어떤 **전문성**이 필요한지 뽑는다.
사람 수를 먼저 정하지 않는다 — 필요한 역할이 몇 개인지가 사람 수를 정한다.

| 기준 | 나눈다 | 합친다 |
|---|---|---|
| 전문성 | 영역이 다르다 | 영역이 겹친다 |
| 병렬성 | 독립 실행 가능하다 | 순차 종속이다 |
| 컨텍스트 | 읽어야 할 것이 많다 | 가볍다 |
| 재사용 | 여러 태스크에서 쓴다 | 한 번만 쓴다 |

**3명의 집중된 팀원이 5명의 산만한 팀원보다 낫다.**

| 계획 규모 | 팀원 수 |
|---|---|
| 태스크 5개 이하 | 1~2명 |
| 태스크 6~12개 | 2~3명 |
| 태스크 13개 이상 | 3명. 넘으면 기능을 쪼갤 때다 |

**한 명이 끝낼 수 있으면 여럿 대신 한 명을 쓴다.** 위임은 정말로 독립적이고
큰 작업에서만 이득이고, 작은 일에 붙이면 비용과 시간만 곱해진다.
실제로 4명을 띄워 같은 파일을 동시에 고친 세션이 있었다.

거의 모든 기능에 들어가는 역할이 셋 있다. 이유 없이 빼지 않는다.

- **계획 검증자** — 구현 전에 계획을 공격한다. **계획의 코드를 컴파일해 본다**
- **구현자** — TDD 사이클을 돈다
- **검증자** — 서버를 띄우고 실제로 호출한다

여기에 이 기능 고유의 전문가를 더한다. 보안이 걸리면 보안 검토자,
동시성이 걸리면 경합 검증자.

### 코드 검토자를 둘 때 축을 셋으로 잡는다

"전부 보라"고 하면 아무것도 안 본다. 이 기능에서 틀리면 가장 비싼 축 둘을
고르고, **셋째 축은 항상 넣는다.**

**셋째 축 — "이 테스트가 의도한 조건을 실제로 만드는가."**

세 세션 연속 여기서 결함이 새어 나갔다. 테스트는 초록인데 아무것도 안 보는 상태다.

| 실제 사례 | 어떻게 초록이었나 |
|---|---|
| 빈 표에 `string_agg` → `COALESCE`가 빈 문자열 | `doesNotContain`이 **자동으로 참**이 된다 |
| "8스레드 동시성" 테스트 | 요청당 커넥션 2개 × Hikari 풀 10 → **실제로는 5개만 겹쳤다** |
| 상한 단언(`isLessThan`) | 프레임워크 기본값이 이미 그 상한 안이라 **구현 전에도 초록** |
| `404가 5건 이하` | **10건이 전부 429여도 통과**한다 |

**네거티브 컨트롤로는 이 축을 못 덮는다.** 그것은 "수정을 되돌리면 빨간불이
되는가"를 묻는데, 위 넷은 수정과 무관하게 처음부터 아무것도 안 보고 있었다.

물어야 할 것 셋 — **단언이 자동으로 참이 되는 입력이 있나** ·
**의도한 동시성이 환경(풀·락·타임아웃)에 막히지 않나** ·
**이 단언을 통과시키는 잘못된 결과가 있나.**

## 2. 실행 모드를 고른다

**팀 모드가 기본이다.** 2명 이상이면 먼저 팀 모드를 검토한다.
팀원끼리 직접 대화하면 한 명의 발견이 다른 사람의 작업 방향을 즉시 바꾼다.
서브에이전트는 그게 안 되고, 모든 정보가 오케스트레이터를 거쳐 지연된다.

### 이 런타임의 팀 도구

**`TeamCreate`는 없다.** 이 세션에는 암묵적 팀이 하나 있고, `name`을 준
에이전트가 자동으로 그 팀에 들어간다. 다른 문서에서 본 도구 이름을 그대로
쓰지 않는다 — 없는 도구를 호출하면 실행 시점에 깨진다.

| 하는 일 | 도구 |
|---|---|
| 팀원 투입 | `Agent({name, subagent_type, run_in_background:true})` |
| 팀원끼리 대화 | `SendMessage({to:"팀원이름", message, summary})` |
| 오케스트레이터에게 보고 | `SendMessage({to:"main", ...})` |
| 공유 작업 목록 | `TaskCreate` → `TaskUpdate({owner:"팀원이름"})` |
| 진행 확인 | `TaskList` · `TaskGet` |

**`name`을 주지 않으면 `SendMessage`로 부를 수 없다.** 팀 모드에서는 반드시 준다.
이름은 에이전트 정의 파일명과 같게 한다 — 그래야 누가 무엇을 하는지 헷갈리지 않는다.

### 모드 비교

| 모드 | 언제 | 대가 |
|---|---|---|
| **팀 (기본)** | 2명 이상이고, 한 명의 발견이 다른 사람 작업에 영향을 준다 | 토큰 비용이 높다 |
| **서브에이전트** | 결과만 넘기면 충분하다. 통신이 구조적으로 불필요하다 | 모든 정보가 나를 거친다 |
| **하이브리드** | 단계마다 성격이 다르다 | 단계 경계에서 산출물이 끊기지 않게 해야 한다 |

### 구현은 직렬로 유지한다

팀 모드라도 **구현자를 여러 명 동시에 돌리지 않는다.** 같은 파일을 건드려
충돌한다. 병렬로 돌릴 수 있는 것은 서로 다른 파일을 보는 역할이다 —
리뷰·검증·조사.

전형적인 자바 기능 개발의 하이브리드 구성:

```
계획 검증        → 단독 (팀 불필요)
구현 태스크 1..N → 직렬. 리뷰어는 태스크 2~3개마다 붙는다 (매 태스크가 아니다)
최종 검증        → 검증자 + 코드 검토자를 병렬로 (보는 파일이 다르다)
```

## 3. 아키텍처 패턴을 고른다

| 패턴 | 형태 | 언제 | 팀 모드 |
|---|---|---|---|
| **파이프라인** | A→B→C→D | 앞 산출물에 강하게 의존 | 이점 제한적 |
| **팬아웃/팬인** | 분배→병렬→통합 | 같은 입력을 다른 관점으로 | **팀으로 해야 한다** |
| **전문가 풀** | 라우터가 골라 호출 | 입력 유형에 따라 처리가 다름 | 서브가 적합 |
| **생성-검증** | 생성→검수→재생성 | 품질 기준이 객관적 | 팀이 유용 |
| **감독자** | 상태 보고 동적 분배 | 작업량이 가변적 | 공유 작업 목록과 맞음 |
| **계층적 위임** | 총괄→팀장→실무자 | 2단계 이내 | 팀 중첩 불가 |

상세는 [references/patterns.md](references/patterns.md).

자바 기능 개발의 기본형은 **파이프라인 + 생성-검증** 복합이다.

**재시도 상한을 반드시 정한다.** 생성-검증에서 상한이 없으면 무한 루프가 된다.
2회를 기본으로 하고, 3회째도 실패하면 사람에게 올린다.

## 4. 에이전트 정의를 만든다

**모든 에이전트는 `.claude/agents/{name}.md` 파일로 정의한다.**
Agent 도구의 prompt에 역할을 직접 넣지 않는다. 파일이어야 다음 세션이 무엇을
왜 했는지 알 수 있고, 협업 프로토콜이 명시돼야 결과가 예측 가능해진다.

**모델은 지정하지 않는다.** 세션 모델이 상속된다. 적어봐야 중복이고,
모델을 바꿀 때 정의 파일을 전부 고쳐야 한다.

**대신 역할마다 `effort`를 정한다.** frontmatter의 `effort`는 세션 값을
덮어쓰고, **안 적으면 세션 값을 그대로 물려받는다** — 즉 안 적으면 전원이
같은 값으로 돈다. 로그만 붙이는 검증자가 구현자와 같은 토큰을 태운다.

| 역할 | effort | 왜 |
|---|---|---|
| 구현자 | `high` | 코드를 실제로 쓴다 |
| 계획 검증자 | `high` | 여기서 놓치면 뒤 태스크가 전부 터진다 |
| 코드 리뷰어 | `medium` | 리뷰 정확도는 낮은 effort에서도 유지된다 |
| 검증자 | `low` | 명령을 돌리고 로그를 그대로 붙이는 일이다 |

`xhigh`·`max`를 기본으로 두지 않는다. 한 역할이 반복해서 막힐 때 **그 역할만** 올린다.

팀 모드면 각 정의에 **`## 팀 통신` 섹션**을 넣는다 — 누구에게 무엇을 보내고
누구에게서 무엇을 받는지. 이게 없으면 팀원들이 서로를 모른 채 각자 일한다.

템플릿과 예시는 [references/agent-template.md](references/agent-template.md).

각 정의에 **절대 규칙 10개와 승격된 규칙 중 그 역할에 걸리는 것을 전문으로
옮긴다.** 에이전트는 `RULES.md`를 읽지 않는다. 번호만 적으면 아무 의미가 없다.
커밋을 남기는 것은 구현자다 — 오케스트레이터만 규칙을 아는 구조는 실패한다.

승격된 규칙(번호 없는 `##` 절)도 역할에 걸리면 같이 옮긴다 — 시험을 쓰는
에이전트에게 「결함을 주입해 빨간불을 먼저 본다」가 없으면, 그 규칙은
오케스트레이터의 머릿속에만 있다 (codex, PR #77).

## 5. 오케스트레이터를 만든다

`.claude/skills/{기능슬러그}-orchestrator/SKILL.md`

개별 에이전트가 "각자 무엇을 어떻게"라면, 오케스트레이터는
**"누가 언제 어떤 순서로"** 다.

담을 것:

- 팀 구성표 (팀원 · 역할 · 입력 · 출력 파일)
- **실행 모드** (팀 / 서브 / 하이브리드. 하이브리드면 단계별로 명시)
- 단계별 실행 순서
- 데이터 전달 — 산출물은 파일, 조율은 `SendMessage`, 상태는 `TaskUpdate`
- 오류 처리 — **1회 재시도, 재실패 시 그 결과 없이 진행하고 보고서에 누락 명시**
- 재시도 상한

## 6. 산출물 규약

```
_workspace/{순번}_{에이전트}_{산출물}.md
```

예: `01_plan-critic_findings.md` · `02_implementer_login-service.md`

- 순번은 실행 순서다. 파일명만 봐도 무슨 순서로 일했는지 보인다
- **중간 산출물을 지우지 않는다.** 사후 검증과 감사 추적의 근거다
- 대용량·구조화된 결과는 파일로, 짧은 조율은 `SendMessage`로

## 7. 기록

2층 `CLAUDE.md`의 변경 이력에 한 줄 남긴다.

```markdown
| 2026-07-29 | 로그인 하네스 (4명, 하이브리드, 파이프라인+생성검증) | .claude/agents/ | - |
```

**에이전트 목록·디렉토리 구조를 쓰지 않는다.** 파일에서 직접 확인 가능하므로
중복이고, 중복은 곧 낡는다.

## 체크리스트

- [ ] `.claude/agents/`가 비어 있는 상태에서 시작했다
- [ ] 모든 에이전트가 파일로 정의됐다 (prompt 직접 주입 없음)
- [ ] 모든 에이전트에 `effort`가 있다 (`model`은 적지 않는다)
- [ ] 팀 모드면 각 정의에 `## 팀 통신` 섹션이 있다
- [ ] 팀 모드면 `Agent` 호출에 `name`을 준다
- [ ] 각 정의에 해당 역할이 지킬 절대 규칙 **과 승격 규칙**이 **전문으로** 들어갔다
- [ ] 계획 검증자·구현자·검증자 세 역할이 있다 (없다면 그 이유가 있다)
- [ ] 오케스트레이터에 실행 모드·재시도 상한·오류 처리가 있다
- [ ] 구현자를 병렬로 돌리는 구성이 아니다
