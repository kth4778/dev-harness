# 아키텍처 패턴 6종

## 1. 파이프라인

```
[분석] → [설계] → [구현] → [검증]
```

앞 에이전트의 출력이 뒤 에이전트의 입력이 된다.

- **언제:** 각 단계가 앞 단계 산출물에 강하게 의존할 때
- **예:** 스키마 → 엔티티 → 서비스 → 컨트롤러
- **주의:** 한 곳이 막히면 전체가 멈춘다. 각 단계를 가능한 독립적으로 설계한다

## 2. 팬아웃/팬인

```
         ┌→ [전문가A] ─┐
[분배] → ├→ [전문가B] ─┼→ [통합]
         └→ [전문가C] ─┘
```

- **언제:** 같은 입력을 서로 다른 관점으로 동시에 봐야 할 때
- **예:** 코드 하나를 보안·성능·설계 관점에서 동시 검토
- **주의:** 통합 단계의 품질이 전체 품질을 결정한다. 통합을 대충 하면 병렬로 얻은 게 사라진다

## 3. 전문가 풀

```
[라우터] → { 전문가A | 전문가B | 전문가C }
```

- **언제:** 입력 유형에 따라 처리가 다를 때
- **예:** 버그 유형에 따라 동시성·성능·로직 전문가 중 하나만 호출
- **주의:** 라우터의 분류 정확도가 전부다. 잘못 분류하면 엉뚱한 전문가가 헤맨다

## 4. 생성-검증

```
[생성] → [검증] → (문제 있으면) → [생성] 재실행
```

- **언제:** 품질 기준이 객관적으로 존재할 때
- **예:** 구현 → 리뷰 → 지적사항 반영
- **주의:** **재시도 상한 2~3회 필수.** 없으면 무한 루프. 상한을 넘으면 사람에게 올린다

## 5. 감독자

```
         ┌→ [워커A]
[감독자] ─┼→ [워커B]   ← 진행 상황을 보며 동적으로 분배
         └→ [워커C]
```

- **언제:** 작업량이 가변적이거나 런타임에 분배를 정해야 할 때
- **팬아웃과의 차이:** 팬아웃은 사전 고정 분배, 감독자는 진행을 보며 조정
- **주의:** 감독자가 병목이 되지 않게 위임 단위를 충분히 크게 잡는다

## 6. 계층적 위임

```
[총괄] → [팀장A] → [실무자A1]
                 → [실무자A2]
       → [팀장B] → [실무자B1]
```

- **언제:** 문제가 자연스럽게 계층으로 분해될 때
- **주의:** **2단계 이내.** 3단계를 넘으면 지연과 컨텍스트 손실이 커진다

# 복합 패턴

실전에서는 단일 패턴보다 조합이 흔하다.

| 조합 | 구성 | 예 |
|---|---|---|
| **파이프라인 + 생성-검증** | 순차 진행하되 각 단계마다 검수 | 자바 기능 개발의 기본형 |
| 팬아웃 + 생성-검증 | 병렬 생성 후 각각 검증 | 여러 모듈 동시 수정 후 모듈별 리뷰 |
| 파이프라인 + 팬아웃 | 순차 중 일부 구간만 병렬 | 설계(순차) → 구현(병렬) → 통합 테스트(순차) |

**자바 백엔드 기능 개발의 기본형은 파이프라인 + 생성-검증이다.**

```
[계획 검증] → [구현 태스크1] → [리뷰] → [구현 태스크2] → [리뷰] → ... → [최종 검증]
                    ↑______________|  (지적 시 재작업, 상한 2회)
```

# 팀 모드로 돌릴 때의 도구

**`TeamCreate`는 이 런타임에 없다.** 다른 문서에서 본 이름을 그대로 쓰지 않는다.
이 세션에는 암묵적 팀이 하나 있고, `name`을 준 에이전트가 자동으로 들어간다.

| 하는 일 | 도구 |
|---|---|
| 팀원 투입 | `Agent({name, subagent_type, run_in_background:true})` |
| 팀원끼리 대화 | `SendMessage({to:"팀원이름", message, summary})` |
| 오케스트레이터에게 | `SendMessage({to:"main", ...})` |
| 작업 등록·할당 | `TaskCreate` → `TaskUpdate({owner:"팀원이름"})` |
| 진행 확인 | `TaskList` · `TaskGet` |

주의할 것:

- **`name`이 없으면 부를 수 없다.** 팀 모드에서는 반드시 준다
- 에이전트의 일반 출력은 다른 에이전트에게 **안 보인다.** `SendMessage`를 써야 한다
- 상태 보고는 JSON 메시지가 아니라 `TaskUpdate`로 한다
- 이름은 최신 것이 이긴다. 같은 이름을 두 번 쓰지 않는다

# 에이전트 타입 고르기

| 타입 | 도구 | 언제 |
|---|---|---|
| 커스텀 (`.claude/agents/`) | 전체 | 역할이 복잡하고 프로토콜이 필요할 때 — **기본값** |
| `general-purpose` | 전체 | 단순 조사이고 프롬프트만으로 충분할 때 |
| `Explore` | 읽기 전용 | 코드 탐색·분석. 실수로 파일을 고치는 것을 막는다 |
| `Plan` | 읽기 전용 | 설계·계획만. 코드 변경 방지 |

빌트인 타입을 쓰더라도 **에이전트 정의 파일은 만든다.** 타입은
`subagent_type` 파라미터로 지정하고, 파일에는 역할·원칙·프로토콜을 담는다.

읽기만 하면 되는 역할에 쓰기 권한을 주지 않는다. **도구를 빼는 것도 설계다** —
"고치지 마라"는 지침보다 고칠 수 없는 구조가 확실하다.
