# 계획 (Phase 2)

**컨텍스트가 0인 엔지니어가 그대로 따라할 수 있는 계획**을 쓴다.
그 사람은 실력은 있지만 이 코드베이스도, 이 도메인도 모르고, 테스트를 싫어한다.

계획이 부실하면 구현 단계에서 터진다. 그때는 이미 코드가 쌓여 있어서
되돌리는 비용이 계획을 다시 쓰는 비용보다 훨씬 크다.

## 먼저: 외부 라이브러리를 실물로 확인한다

계획에 새 라이브러리·프레임워크 기능이 들어가면, **쓰기 전에 확인한다.**

| 확인할 것 | 방법 |
|---|---|
| 좌표·버전 | 실제 저장소·문서에서. 기억으로 쓰지 않는다 |
| **패키지 경로** | 메이저 버전이 바뀌면 패키지가 옮겨간다 |
| 시그니처 | 인자 순서·타입·반환형 |
| 이 프로젝트의 버전과 호환되나 | 상위 프레임워크 버전 확인 |

좌표만 맞고 패키지 경로가 틀리면 계획대로 짜도 컴파일이 안 된다.
**둘 다 확인한다.**

## 파일 구조를 먼저 그린다

태스크를 나누기 전에 어떤 파일이 생기고 바뀌는지, 각 파일이 무엇을 책임지는지
적는다. 여기서 분해가 결정된다.

- 파일 하나에 책임 하나
- 같이 바뀌는 것은 같이 둔다. 기술 계층이 아니라 **책임**으로 나눈다
- 기존 코드베이스의 패턴을 따른다. 마음대로 재구성하지 않는다

## 태스크 크기

태스크 = **자기 테스트 사이클을 갖고, 리뷰어가 독립적으로 반려할 수 있는 최소 단위.**

- 설정·스캐폴딩·문서는 그것을 필요로 하는 태스크에 **접어 넣는다**
- 리뷰어가 A는 승인하고 B는 반려할 수 있을 때만 A와 B를 나눈다
- **코드와 그 코드를 검증하는 테스트는 같은 태스크에** 둔다

각 단계는 2~5분짜리 한 동작이다.

```
- [ ] 1단계: 실패하는 테스트를 쓴다
- [ ] 2단계: 실패를 확인한다
- [ ] 3단계: 통과시키는 최소 코드를 쓴다
- [ ] 4단계: 통과를 확인한다
- [ ] 5단계: 커밋한다
```

## 빈칸을 남기지 않는다

다음은 **계획 실패**다. 절대 쓰지 않는다.

- "TBD", "나중에", "상세는 구현 시"
- "적절히 오류 처리" / "검증 추가" / "엣지 케이스 처리"
- "위 내용에 대한 테스트 작성" (테스트 코드 없이)
- "태스크 N과 비슷하게" — 코드를 다시 쓴다. 읽는 사람이 순서대로 읽지 않을 수 있다
- 어떤 태스크에도 정의되지 않은 타입·메서드 참조

## 자체 검토

계획을 다 쓴 뒤 PRD를 새 눈으로 다시 보고 대조한다.

1. **누락** — PRD의 각 항목을 구현하는 태스크를 짚을 수 있나? 없으면 태스크를 추가한다
2. **빈칸** — 위 목록의 표현이 남아 있나? 고친다
3. **이름 일치** — 3번 태스크의 `clearLayers()`가 7번에서 `clearFullLayers()`로 바뀌지 않았나?
4. **검증 동거** — 각 태스크에 그 코드를 검증하는 테스트가 같이 있나?
5. **라이브러리** — 새로 쓰는 것의 좌표·패키지 경로를 실물로 확인했나?

문제가 있으면 그 자리에서 고친다. 다시 검토할 필요는 없다.
