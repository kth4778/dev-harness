# 자바·스프링 TDD (Phase 4)

## 철칙

```
테스트 없이 짠 구현 코드는 없다
```

구현을 먼저 썼다면 **지운다.** 예외 없다.

- "참고용으로 남긴다" — 안 된다
- "테스트 쓰면서 다듬는다" — 안 된다
- "이미 손으로 확인했다" — 손으로 확인한 건 지금 한 번이다. 테스트는 앞으로 매번이다
- **규칙의 문구를 어기는 것이 규칙의 정신을 어기는 것이다**

## 사이클

```
RED    실패하는 테스트를 쓴다
  ↓
확인   실행해서 실패를 눈으로 본다  ← 이 단계를 건너뛰지 않는다
  ↓
GREEN  통과시키는 최소 코드를 쓴다
  ↓
확인   실행해서 통과를 본다
  ↓
커밋   1사이클 = 1커밋
```

**실패를 확인하는 단계가 핵심이다.** 실패를 안 본 테스트는 왜 통과하는지 모른다.
단언을 잘못 써서 무엇을 넣어도 통과하는 테스트를 수없이 본다.

실패 이유도 본다. 컴파일 오류로 실패한 것과 단언으로 실패한 것은 다르다.
**의도한 이유로 실패했는지** 확인한다.

## 스프링에서 어느 테스트를 쓰나

무거운 테스트를 기본값으로 삼지 않는다. **가장 가벼운 것부터 고른다.**

| 종류 | 애너테이션 | 언제 | 속도 |
|---|---|---|---|
| **순수 단위** | 없음 | 로직·계산·검증 규칙. 스프링이 필요 없다 | 밀리초 |
| **슬라이스** | `@WebMvcTest` · `@DataJpaTest` | 컨트롤러 매핑, 리포지토리 쿼리 | 초 |
| **통합** | `@SpringBootTest` | 계층을 가로지르는 흐름, 트랜잭션, 동시성 | 수십 초 |

대부분의 비즈니스 로직은 **순수 단위 테스트로 충분하다.** 서비스가
`@SpringBootTest`를 요구한다면 의존이 과한 것이고, 그건 설계 신호다.

## 안티패턴

| 하는 짓 | 왜 나쁜가 |
|---|---|
| 단언이 없는 테스트 | 무엇을 넣어도 통과한다. 테스트가 아니다 |
| `assertThat(x).isNotNull()` 만 | null만 아니면 통과한다. 값을 검증하지 않는다 |
| 구현을 그대로 베낀 단언 | 구현이 틀리면 테스트도 같이 틀린다 |
| 테스트 하나에 시나리오 여러 개 | 실패했을 때 어디가 깨졌는지 모른다 |
| `Thread.sleep()`으로 대기 | 느리고 불안정하다. 조건 기반으로 기다린다 |
| 테스트 순서에 의존 | 단독 실행하면 깨진다. 각 테스트는 자기 데이터를 만든다 |
| 모든 것을 목으로 | 목끼리만 대화하는 테스트는 실제 동작을 검증하지 않는다 |

## 테스트 이름

한글로 **행동을 서술**한다. 실패 목록만 읽어도 무엇이 깨졌는지 알아야 한다.

```java
void 활성_키가_있으면_발급이_거부된다()
void 동시_발급_2건이면_1건만_성공한다()
void 헤더가_없으면_400을_반환한다()
```

**구현을 먼저 썼다면 지운다**(규칙 3). 남겨두고 테스트를 덧붙이면 그 테스트는
바로 통과하고, 무엇을 증명했는지 알 수 없게 된다.

## 커밋

**1사이클 = 1커밋.** 테스트와 구현을 같은 커밋에 넣는다.

커밋 시점에 테스트가 통과한 상태여야 한다. 훅이 검사하지만, 훅이 없어도
지킨다 — 검증 안 된 커밋은 히스토리를 못 믿게 만든다.
